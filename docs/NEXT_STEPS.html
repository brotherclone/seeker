Seeker is an idea engine for creative tech. It draws three cards from independent decks, generates an idea of the form "a/an X that does Y because Z", then has critics debate it and a blind judge rank it on three separate Elo axes (novelty, feasibility, promise). The top three by promise survive and are mutated into the next round. Start with docs/concept.md, then CLAUDE.md.

Rules you must follow

  • OpenSpec for every change. Propose with /opsx:propose and implement with /opsx:apply. Work on feature/<change-name> branches cut from develop, and merge through a PR. Never commit to develop or main.
  • Ontology first. Define any new concept in the LinkML schema under schema/ before code uses it. Then run make lint and make schema, and keep the Pydantic conformance test green with make test.
  • Python style: Pydantic v2 models that mirror LinkML. No Any, no dict payloads, no dataclasses or TypedDicts. Use named constrained scalar types.
  • Obsidian vault (/Users/gabrielwalsh/Documents/Claude/Projects/Seeker/): record decisions in Decisions/YYYY-MM-DD <title>.md, and update Ontology/<Class>.md in the same change as the schema. Every note links back to [[Seeker]].
  • Never hard-code paths. Read them from seeker.yaml. Run everything through uv run.
  • Leave the schedule workspace alone. /Users/gabrielwalsh/Sites/seeker-schedule is a git worktree detached at origin/develop, and the LaunchAgent runs there. Never git switch, commit or edit files in it. Move it only with uv run seeker-schedule workspace update. Branch freely in the main checkout. Schedule commands run from there act on the workspace anyway, because .env sets SEEKER_SCHEDULE_WORKSPACE.
  • Ask Gabe first before merging PRs, signing off reviews, spending API money outside the scheduled job, or changing the schedule.
